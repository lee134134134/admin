# 测试规范

## 质量门禁（NON-NEGOTIABLE）

**任何代码改动完成后，至少按序执行：**

```bash
pnpm type-check     # 1. 类型检查（vue-tsc --noEmit）—— 最低要求
pnpm lint           # 2. ESLint 静态检查
pnpm format:check   # 3. Prettier 格式检查
pnpm build          # 4. 生产构建（含类型检查）
```

| 门禁 | 命令 | 不通过则 |
|------|------|----------|
| 类型 | `pnpm type-check` | **不得交付**，必须修复 |
| 静态 | `pnpm lint` | 不得交付；可用 `pnpm lint:fix` 自动修复 |
| 格式 | `pnpm format:check` | 用 `pnpm format` 自动修复 |
| 构建 | `pnpm build` | 不得交付 |

- `pnpm lint:fix` / `pnpm format` 只允许**自动修复**，禁止为通过 lint 手工重构业务逻辑
- 若规则确实不适合本项目，改 `eslint.config.js` 并加注释说明，**不要**用 `eslint-disable` 逐行压制

## Git Hooks

- `husky` + `lint-staged` 在 **pre-commit** 自动跑格式化与 lint（作用于暂存文件）
- commit 时若被 hook 拦下：先修复再提交，**禁止 `git commit --no-serve` / `--no-verify` 绕过**
- `type-check` 较慢，不挂在 pre-commit，由交付前手动执行

## 类型安全（NON-NEGOTIABLE）

- 禁止 `any`、禁止 `@ts-ignore`（见 `02-编码规范`）
- API 出入参必须有显式类型（见 `05-API规范`）
- 组件 Props / Emits 必须显式声明（见 `04-组件规范`）

## 单元测试现状

> **本项目当前未引入测试框架**（无 Vitest / Playwright / 测试文件）。

- 因此**现阶段不强制要求新增测试用例**；上述四条门禁即为交付标准
- 但 `references/workflows/testing/*` 等依赖静态检查的测试工作流，**执行前需先补齐测试基础设施**

### 何时应引入 Vitest（触发条件）

满足任一即应向用户提出补齐建议，并在引入后更新本文件：

1. 出现**纯函数核心逻辑**（日期/区间计算、数据变换、权限判断）且被多处复用
2. 同一 bug 修复过两次（回归风险高）
3. 用户明确要求补测试

### 引入后的预设要求

- 框架：Vitest + `@vue/test-utils`；配置 `vitest.config.ts` 复用 `vite.config.ts` 的 `@` 别名
- 覆盖重点：**业务逻辑**优先于组件渲染；不做无意义的快照测试
- 测试文件：与源文件同目录 `*.spec.ts`，或集中 `src/__tests__/`
- 新增门禁：`pnpm test` 加入上表，并同步 `.agents/skills/` 中的验收步骤

## UI 验收（补充）

- 代码门禁通过**不代表** UI 合格
- 有设计稿的改动，实现后按 `.agents/skills/ui-verification` 用浏览器与设计稿比对，产出 P0/P1/P2 问题清单
- 详见 `.agents/skills/ui-verification/SKILL.md`
