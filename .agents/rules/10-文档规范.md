# 文档规范

## 注释原则（NON-NEGOTIABLE）

**注释解释「为什么」，不解释「做什么」。**

```ts
// ✅ 为什么: 拦截器已注入 token, 业务侧重复构造会导致登录后首个请求鉴权失败
const data = await getCalendarEvents(start, end)

// ❌ 做什么: 获取日历事件
const data = await getCalendarEvents(start, end)
```

- 代码能自解释时**不写注释**，不要写「设置值」「调用接口」这类复述
- 注释用**中文**，半角冒号 + 空格：`// 代理到后端服务，按实际后端地址调整`
- 注释与代码同步修改，**禁止留下过期注释**（改了逻辑不改注释比没注释更糟）

## 何时必须写注释

| 场景 | 形式 |
|------|------|
| 导出的 API / 工具函数 | JSDoc `/** */` |
| 复杂业务逻辑、非直观算法 | 行注释说明动机 |
| 临时方案 / 已知缺陷 / 待办 | `// TODO(<原因>): ...`，便于检索 |
| 兼容性 workaround | 注释说明触发条件，**否则后来者会删掉它** |
| 魔法数字 / 色值 | 注释来源（如「设计稿 token」） |

```ts
/** 获取工作台统计数据(占位接口, 后端就绪后对齐) */
export function getDashboardStats() {
  return httpGet<DashboardStats>('/dashboard/stats')
}
```

## JSDoc 用法

- 用于**导出**的函数、接口、组件 props
- 结构：一句话说明 + `@param` / `@returns`（仅在类型不能表达时）
- **禁止**复述函数名：`/** 获取日历事件 */ export function getCalendarEvents()` → 值得补的是取值范围、副作用、异常行为
- 接口字段有业务含义或枚举约束时，写在字段上方而不是文件头

## 文件头

- 一般文件**不需要**文件头注释（文件名已说明）
- 仅在文件有非常规职责时写 3~5 行块注释（如 `request.ts` 说明拦截器行为）

## Vue 组件注释

- `<script setup>` 内对非直观逻辑加行注释
- 复杂模板区域可用 `<!-- 区域名 -->` 分段，但**不要**给每个元素加注释
- Props 用 `defineProps` 的接口定义本身即文档，不必重复

## README 与交付文档

- 本项目存在两份顶层协作文档：`AGENTS.md`（主）与 `CLAUDE.md`（Claude 专用）
  - **两者内容必须保持一致**；冲突时**以实际代码为准**，并同步更新两份
- 规范类文档放在 `.agents/rules/`，**改完必须同步对应 `README.md` 索引**
- 技能类放在 `.agents/skills/`，同步 `skills/README.md` 索引

## 文档结构要求

- 用标题层级清晰组织；表格优于长段落
- 命令用行内代码或代码块，**可直接复制执行**
- 约束写成可判断的是/否，**避免**「尽量」「最好」这类不可验证的措辞
  - 需要软约束时明确标注 `推荐`，与 `NON-NEGOTIABLE` 区分

## 变更记录

- 不维护手写 CHANGELOG；变更历史交给 git
- 重大约定变更（如目录结构、依赖选型）需同步更新 `01-项目概述` 与 `03-项目结构`
